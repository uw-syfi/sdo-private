# Responder token/time audit: decisions log

This log covers a read-only audit of where SDO's responder spends tokens and wall-clock time,
using only existing SREGym run records (no LLM or Codex CLI call was made; the weekly Codex quota
was at 90% on 2026-09-28, resetting 2026-10-03; no kind cluster was created or touched). It backs
the per-request breakdown and ranked trims reported to the coordinator, and records what was
actually implemented versus proposed.

  fresh arms, 2 stages each; `third_party/sregym/logs/20260927_182519_pipeline_sdo-codex-luna-persistent`
  and its 5 sibling pipeline directories, plus `20260927_205946_codex` for the Codex x5 baseline).
  This is the same data already tabulated in `benchmarks/sregym/experiments/luna_reuse_DECISIONS.md`

- **Four `network_policy_block` SDO pipeline runs**, all on `codex:gpt-6-luna`, medium effort, run
  today (`20260928_074550`, `081908`, `082009`, `082110`, all under
  `/mnt/data/shli/sdo-worktrees/luna-reuse-merge/third_party/sregym/logs/`), each analyzed with
  `benchmarks.sregym.analysis.incident_cost` (outputs already saved in this session's scratchpad as

## Validity

`benchmarks/sregym/analysis/run_validity.py` exists only on local branch `vic/feat/harness-assurance`
(read via `git show`, not merged). Its exact API (`problem_results_dirs`, `read_result_row`,
`with_mitigation_applied` as public names) has diverged from this branch's
`benchmarks/sregym/analysis/incident_cost.py` (still private `_problem_results_dirs`,
`_with_mitigation_applied`; no `read_result_row`), so it does not import cleanly here without changes
to `incident_cost.py` itself, which is out of scope for a read-only audit. Rather than patch it
speculatively (risking a validity checker that silently classifies runs wrong), its documented
criteria were applied by hand to every run used above:

- every run has a result row and a completed oracle verdict (`Diagnosis.success`/`Mitigation.success`
  both present, read by `incident_cost.read_verdict`);
- every run's token totals reconcile (the `ic_*.txt` tool ran to completion with responder and
  reflection token breakdowns and no reconciliation error);
- TTD never exceeds TTM in any row (checked across all 4 `network_policy_block` runs and the 6
  persistent-controller stages);
- no agent-install or quota-exhaustion error appears in any rollout or driver log;
- the three parallel `network_policy_block` reruns used separate kind clusters (`luna-w0`/`w1`/`w2`,
  distinct kubeconfigs in the scratchpad), so their overlapping wall-clock windows are lane-isolated,
  not a shared-cluster confound.

All runs used in this audit are treated as valid under those criteria. None was excluded.

## Finding 1: request count, not per-request size, drives the responder/reflection gap

Per-request traces of the persistent-controller rollouts
(`third_party/sregym/logs/20260927_182519_pipeline_sdo-codex-luna-persistent/stage_0_first-incident/.../rollout-*.jsonl`)
show Codex's prompt caching model: each model response's `cached_input_tokens` is a full re-read of
the growing conversation prefix (system prompt + every earlier message and tool output), and
`uncached_input_tokens` is only the small delta added since the previous response (500-4,000 tokens
in the observed trace, mostly the previous tool call's own output). The first-incident responder
session took 23 requests; the Codex baseline's mean was 10.2. Because every request re-pays the
*entire* accumulated prefix as a cache read, the cost is closer to quadratic than linear in request
count: SDO's 574K mean cached input on stage 0 (`luna_reuse_DECISIONS.md` 3.3) is not because any
one turn is bloated, it is because there are about twice as many turns, each re-reading a growing
context. **Implication: cutting request count is the highest-leverage lever, ahead of trimming any
single prompt section.**

## Finding 2: two concrete, avoidable sources of extra requests

1. **`.sdo/arch.md` is never inlined, unlike `goal.md`.** The stage-0 rollout's very first tool call
   was `cat .sdo/arch.md && cat kubernetes/geo/mongodb-geo-deployment.yaml && rg ...`, a single
   22,311-character combined dump — the single largest tool output in the whole session. `arch.md` in
   that run's workspace was 5,806 characters, i.e., it fits the same kind of cap `goal.md` already
   gets (`_GOAL_INLINE_MAX_CHARS = 4_000`; `arch.md` needs a slightly larger one, since it is
   deployer-owned and typically a bit longer than the health objective). Every cold incident pays at
   least one shell round trip to (re)discover it.
2. **Manual poll-and-recheck turns.** The stage-1 (warm) rollout
   (`.../stage_1_reused-incident/.../rollout-2026-09-27T18-43-50-*.jsonl`) shows two
   `tools.write_stdin({session_id, chars:"", yield_time_ms:1000, ...})` calls: the responder starts a
   repair or verification command in the background, then returns in a **separate model turn** just to
   check whether it finished. Each such turn cost about as much context as any other turn in that
   10-request session (roughly 18.5K and 19.5K tokens respectively, including the full re-read of the
   session so far) — close to 20% of that run's 185K raw total for two turns that added no new
   information. A single blocking command (`kubectl rollout status ... --timeout=`, `kubectl wait
   --for=condition=... --timeout=`, or a long enough `yield_time_ms` up front) would fold the wait into
   the same turn as the command that started it.

## Finding 3: the historical outcome record is unbounded and resent whole on every reflection

`sdo/agent_runtime/responder/reflection.py`'s `_learning_request` embeds
`outcome.model_dump_json(indent=2)` for the current outcome and
`json.dumps([record.model_dump(...) for record in history])` for **every** past `OutcomeRecord`
(`sdo/operational_memory/repository.py:outcomes()` reads the whole of `.sdo/outcomes.jsonl`, with no
cap). Each `OutcomeRecord` carries its own unbounded `detector_history` and `findings` (each finding's
full `evidence` string) — exactly the raw, per-timestamp data the *responder's own* prompt already
compacts via `_detector_evidence()` (the v2 fix in `luna_reuse_DECISIONS.md`, "detector_history is
removed from the prompt's request JSON..."). That fix was never applied to reflection's view of past
outcomes. In the runs audited here `history` is 0-1 entries, so it is not yet the dominant cost, but
it grows with every incident an operator's controller ever resolves and is the sharpest edge case for
a long-running deployment (the paper's target regime, not a short benchmark).

**Not implemented.** Changing what reflection is shown about past outcomes changes the evidence
its own generalization reasoning runs on ("ground structural changes in the supplied history"), which
the brief marks as learning semantics — a proposal only. See ranked trims below.

## Finding 4: Codex CLI harness boilerplate is resent every turn

Three `developer`-role messages appear before the first user turn: `<skills_instructions>` (4,694
chars), `<multi_agent_role>` (2,429 chars), `<multi_agent_mode>` (271 chars) — none of it SDO's own
prompt; it is the Codex CLI's own skills/multi-agent-collaboration feature framing, irrelevant to a
single-shot incident responder. At ~7.4K chars (~1.85K tokens) it is cached after turn 1, but it is
still re-read on every one of the ~20+ requests in a cold session, contributing on the order of
30-40K cache-read tokens session-wide. **Not implemented**: disabling it would require a Codex CLI
config flag this audit could not verify live (quota capped, no Codex run permitted), and passing an
unverified flag risks silently breaking every future run. Proposal only, pending quota reset.

## Ranked trims

| # | Trim | Est. savings | Risk | Status |
|---|---|---|---|---|
| 1 | Inline `.sdo/arch.md` (capped, like `goal.md`) | removes >=1 request per cold incident (~15-30K raw tokens directly, plus the knock-on cache-read reduction on every later request in the same session, since the whole session is one fewer turn shorter) | Low: same file the agent already reads; only removes a redundant tool round trip, changes no incident information | **Implemented** (`a2c5e...`, see below) |
| 2 | Prompt guidance: prefer one blocking wait over manual poll-and-recheck turns | ~2 requests removed per session where the responder currently polls (observed ~38K tokens for 2 such turns in a 10-request, 185K-token warm repeat — roughly 20%) | Low: adds tool-usage guidance only; does not change what the responder knows about the incident or any output schema | **Implemented** |
| 3 | Compact reflection's `history` (past `OutcomeRecord`s) the way the responder's own request already compacts `detector_history`, and cap `findings[].evidence` length in old entries | grows without bound today; even at n=1-3 prior outcomes it is already a meaningful share of reflection's 350-624K raw, and it is the only cost in this audit that scales with an operator's incident count rather than staying flat | Medium-high: changes the evidence reflection's own generalization step runs on for past incidents | **Proposal only** |
| 4 | Default the persistent controller's reflection session to `fresh` instead of `resume` | `luna_reuse_DECISIONS.md` 3.3 measured fresh reflection at 553K vs resumed reflection's 690K raw (-27%) with no measured speed or memory-quality cost, at n=3 per arm | Medium: changes the shape of context reflection reasons from (a compact brief instead of the resumed transcript); the brief's own next-action note asks for a larger-n confirmation first | **Proposal only** (already flagged as a "next action" in `luna_reuse_DECISIONS.md`; this audit adds no new evidence beyond what is there) |
| 5 | Disable Codex CLI's skills/multi-agent boilerplate (`skills_instructions`, `multi_agent_role/mode`) for the single-shot responder | ~30-40K cache-read tokens/session (rough, from observed sizes and request counts) | Medium: requires a Codex CLI config flag verified only by a live run, which the quota freeze does not allow | **Proposal only**, verify after 2026-10-03 |
| 6 | Cap the responder's own live tool outputs (e.g. discourage full `-o yaml` dumps in favor of `-o jsonpath=`/`--no-headers`) | Hard to estimate without a live run; the one 22K-char dump observed is now mostly avoided by trim #1 | Low-medium: guidance only, but its effect on the model's own command choices is unverified without a live run | **Proposal only**, revisit after trims #1-2 are measured |

## Implemented

- **`1816e9c`: inline `.sdo/arch.md` in the responder prompt, and steer away from manual poll turns.**
  `sdo/agent_runtime/responder/codex.py`: new `_inlined_architecture_summary()`, mirroring
  `_inlined_health_objective()`, capped at `_ARCH_INLINE_MAX_CHARS = 8_000` (goal.md's own cap is
  4,000; arch.md is deployer-owned, read-only for the responder, and empirically a bit longer, so it
  gets the same cap as the warm playbook text). Falls back to path-only above the cap, identically to
  `goal.md`. Test-first:
  `tests/unit/sdo/agent_runtime/responder/test_codex_responder.py::test_prompt_inlines_a_small_architecture_summary`.
- **Prompt guidance against manual poll-and-recheck turns.** `sdo/agent_runtime/responder/codex.py`
  `_verification_instructions()` (shared by both the warm and cold paths) now opens with an
  instruction to prefer one blocking command (naming `kubectl rollout status ... --timeout=` and
  `kubectl wait ... --timeout=`) over starting a command in the background and returning in a later
  turn to check on it. Test-first:
  `tests/unit/sdo/agent_runtime/responder/test_codex_responder.py::test_every_path_prefers_one_blocking_wait_over_manual_poll_turns`.

## Not implemented (explicitly out of scope per the brief)

- Compacting reflection's `history`/`detector_history` (Finding 3).
- Defaulting `reflection_session` to `fresh` (already an open "next action" in `luna_reuse_DECISIONS.md`).
- Any Codex CLI invocation flag change (Codex CLI harness boilerplate, tool-output token caps) that
  cannot be verified without a live Codex run while the weekly quota is at 90% (resets 2026-10-03).

## First-incident token trim (phase-1 reflection audit, 2026-09-29)

Offline analysis only: no LLM call, no cluster, no image rebuild. It backs branch
`vic/feat/first-incident-token-trim` (off `vic/exp/phase1-run` at `9f7dddf`).

### Data and method

- Four SDO pipelines `20260928_2322*..2328*_pipeline_assure-p1-sdo-{a,b,c,d}` (read only, under
  `.claude/worktrees/agent-abba78c07e386ad4a/third_party/sregym/logs/`), first-encounter stages only
  (`stage_*_r1-*`): 16 responder sessions, 12 of which triggered an LLM reflection (the other 4 were exact-match repeats
  that the broker skips deterministically, or a 1-request no-change).
- Per-request numbers come from the Codex rollout `token_count` events (`last_token_usage`), one rollout per incident.
  The resumed reflection is the second task of the responder's rollout. Cumulative stage folders repeat earlier sessions,
  so each session file is counted once.
- Weighted tokens use PLAN.md weights: uncached 1, cache read 0.1, output 8 (reasoning is part of output).
- Prompt sizes use `o200k_base` (3.93-4.08 chars per token on these prompts; the replay tool uses 4.0).

### Decisions

1. **Bound the outcome sections of the reflection request (implemented).**
   `sdo/agent_runtime/responder/reflection_outcomes.py`: the current outcome keeps every field verbatim except
   `detector_history`, which is run-length encoded per detector (every status or fingerprint transition kept, with first
   and last timestamp and count); prior incidents are compact summaries (findings without evidence, root causes,
   repair actions, playbooks, verification verdicts, collapsed detector history); the current incident is no longer
   repeated inside its own history. This applies Finding 3 above, which was a proposal only when history held 0-1
   entries; in the phase-1 controller it held 1-6.
   - Offline estimate (deterministic replay of the 12 recorded reflection requests with
     `python -m benchmarks.sregym.analysis.reflection_prompt_replay <pipeline stage dirs>`): 124.7K to 47.9K outcome
     tokens, **76.8K prompt tokens saved, 153,235 weighted tokens, 12.8K per reflection, 5.4% of first-incident cost
     (8.2% of reflection)**. It grows with history: 4.9K-9.5K weighted with no prior outcome and 19.6K-22.1K with 5 (the
     mean over the recorded reflections with 3 or more prior outcomes is 20.5K).
   - Quality: the reflection output contract, the SDK reference, memory rules and the topology review are untouched.
     What is dropped is raw evidence text and per-timestamp evaluations of past incidents. Risk: low.
2. **Default the first reflection to a fresh session (implemented).** `DEFAULT_REFLECTION_SESSION = "fresh"` is now the
   default of `BrokerService`, the broker CLI, `ControllerInstallConfig`, the SREGym driver, the assurance CLI and
   fastloop. `resume` stays selectable. Receipts already accept `same_session_reflection=false` for `fresh`.
   - Offline estimate: small. Dropping the resumed responder transcript removes about 8.6K tokens from every request, but
     the brief adds up to about 8K, so the deterministic difference is within 0-3K weighted per reflection (under 1%).
   - Measured, not offline: `luna_reuse_DECISIONS.md` 3.3 measured fresh at 553K vs resumed 690K raw and 149K vs 204K
     weighted (-27% of reflection, n=3 per arm, one outlier). If that holds it is about -18% of a first incident. The
     mechanism is plausibly the cold-cache resume (first request 37.1K uncached) plus a shorter session. Confidence: low
     to medium; the canary must confirm. Risk: reflection no longer sees the responder's own reasoning, only the brief.
3. **Give reflection a worked incident detector and one final verification command (implemented, prompt only).**
   - `INCIDENT_DETECTOR_EXAMPLE_FILES` in `reflection.py` is a `detector.go` plus `detector_test.go` (2.7K chars, about
     0.7K tokens) that compiled and passed under `go test` against `controller/sdk` when written, with the
     `sdk.ObjectRefFrom` and `sdktest.Snapshot` usage that recorded reflections learned by reading health detectors. A
     unit test keeps it gofmt-clean. Prompt says not to read health detector source.
   - The self-check rules now ask to batch edits and verify once, after the last edit, with one command chaining
     `chmod +x`, `bash -n`, `gofmt -l`, `draft-test`, and `memory_check`, and not to re-read the edits with git or cat.
     The validation contract (memory check, draft-test scope, the broker validator) is unchanged.
   - Expected: removes about 1 to 3 read requests in the reflections that have no incident detector to copy (5 of 12)
     and about 1 memory-check or review request per reflection: 3 to 5% of a first incident, plus about 1.4K weighted of
     added prompt. Behavioural, so unverified offline. Risk: the agent may copy the example's shape too literally; the
     validator and the near-miss test requirement still apply.

Expected total: about 8% to 28% off a first incident (the low end is fix 1 alone plus half of fix 3; the high end
includes the measured -27% fresh effect on reflection, and the fixes overlap so they do not add exactly). That moves
the first-encounter ratio including reflection from 1.88x to roughly 1.4x-1.7x Codex. It does not reach parity: reflection
output (21.8% of a first incident) is the deliverable and is left alone. **The actual savings get measured in the next
live canary**: compare per-incident `reflection_usage` and the responder-turn requests against the phase-1 numbers above.

Commits: `9d5c8f4` (fix 1), `049389a` (fix 2), `3a88269` (fix 3), `3cb0d67` (replay tool).

### Considered and not done

- Cap tool-output size: all reflection tool outputs total 206K chars over 12 reflections (about 4.3K tokens each), the
  largest single output is 8K chars. A cap saves under 1%.
- Fewer validator round trips through up-front schema hints: there were no broker rejections to remove. The remaining
  round trips are the agent's own self-checks, covered by fix 3.
- Inline `.sdo/playbooks/README.md` and `manifest.yaml` in the request: read in 9 of 12 reflections, but the inline text
  (about 2.5K tokens x 2.1) costs about as much as the request it saves; revisit if the manifest stays small.
- Responder-side trims: responder polling and prompt size were handled in `1816e9c`; first-request harness base (about
  18.5K tokens) belongs to the Codex CLI, not SDO.
