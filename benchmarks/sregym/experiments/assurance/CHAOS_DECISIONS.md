# Scripted responder, chaos and soak: decisions log

Goal: high assurance, with no LLM quota spent, that the reimplemented prototype's full incident path is solid. A deterministic scripted responder replaces only the model; the real controller, responder Job, broker, reflection, closure gate, receipts and run records run unchanged. Branch `vic/feat/scripted-responder-chaos`, based on `origin/vic/exp/feedback-loop-e2e` at `f0ae5c2`. Each entry states what was chosen, the alternatives, and why.

## Where the model is replaced

- **Decision: replace the `codex` binary, not an SDO interface.** `benchmarks/sregym/assurance/scripted_codex/` is a stdlib-only stand-in for the Codex CLI. It speaks `codex exec --json` (the events agentshim's real Codex parser reads) and writes the session rollout under `$CODEX_HOME/sessions` (the `token_count` events SDO's accounting and `incident_cost` read). It is installed into test images only (`Dockerfile.scripted`, tags `:assure`), where it replaces the real `codex` and `claude` CLIs.
  - Everything above it is real: agentshim's host executor and stream parser, `run_structured_turn` (rollout-delta accounting, `SDO_TURN_USAGE_LOG`), `execute_incident`, the responder Job and result ConfigMap, the Go controller's dispatch and closure gate, the broker's proposal/outcome/reflection commits, validator Jobs, controller rollout of learned detectors, receipts and the fast loop's records.
  - Alternatives rejected:
    - a new `SDO_AGENT_PROVIDER=scripted` backend in `libs/agent_cli` or `sdo/`: puts a test double in production paths, and skips agentshim, rollout accounting and session resume, where several past bugs were (double-counted resumed reflection tokens);
    - agentshim's `FakeExecutor`: in-process only; it cannot run inside the responder Job and the controller pod.
  - No production file changed for the scripted responder. Production code does not import it.
- **Faithful quirks.** Like the real CLI, `turn.completed` reports the session's *cumulative* usage (so a resumed reflection reports the responder's tokens too), and `codex exec resume` of a session with no rollout fails with `thread/resume failed: no rollout found`. The usage per model response is a deterministic function of the directive seed, the turn kind and the response index, with distinct offsets per kind, so a double-counted or dropped turn is a mismatch, never noise.
- **Model id and provider.** Every scripted run uses provider `codex` and model `gpt-6-luna` (the coordinator's 2026-09-28 rule), so the usage records have the real Codex shape. No Claude or other-provider path was added.
- **Nothing can reach a model.**
  - the scripted images contain no model CLI (`build_images.sh` checks `! command -v claude`);
  - the scripted CLI refuses any turn that is not an SDO responder or reflection turn (exit 3, "no scripted plan"), so an unplanned model call fails loudly instead of being faked;
  - the harness's host lifecycle is reuse-only: it raises instead of falling back to a model-backed lifecycle;
  - the harness process points `HOME` and `CODEX_HOME` at an empty directory and sets a placeholder `OPENAI_API_KEY`, so `install_controller`, which copies host credentials into a missing Secret, can only copy the placeholder. The SREGym worker keeps the original `HOME` (uv cache).
  - `assurance run` refuses images without the `sdo.dev/scripted-codex=true` label.

## How a scripted incident is planned

- **Directive per incident, bound at first use.** The harness writes ConfigMap `sdo-scripted-directive` in `<app>-sdo` just before it injects the fault. The first responder turn copies it into `sdo-scripted-bind-<sha(incident id)>`; restarted responder Jobs and later reflection turns read the binding, so moving on to the next incident can never change an earlier incident's plan.
  - The responder SA may get/create ConfigMaps in the controller namespace (it publishes its result there), and so may the controller pod. The app namespace is untouched, so the controller's configuration diff never sees the harness.
- **The directive names the fault class and target; object names come from live state.** The NetworkPolicy to delete is the one `kubectl get networkpolicy -o json` shows isolating the target; the missing ConfigMap is the Deployment volume that `kubectl get configmap` cannot find, and its manifest is found under `kubernetes/` in the worktree. A plan whose fault live state does not show stops with a failed result.
- **Mitigation modes:** `correct`; `wrong_then_correct` (rollout-restart the target, `sdo incident status` stays unhealthy, then the real repair); `wrong_only_honest` (the restart, then an honest `failed` result); `wrong_only_claimed` (the restart, then a `completed` result claiming a wrong cause and a passing check, the dangerous case).
- **Reflection** writes a real incident detector (Go, with matching and near-miss tests), a playbook with `repair.sh`/`verify.sh`, the manifest entry and the playbook index line, then runs SDO's `memory_check`. Every template passes `memory_check` and `check_cli draft-test` in unit tests. After `wrong_only_claimed` it encodes the *claimed* (wrong) cause, detector `wedged-workload-restart`, because that is what a reflecting agent that believed its fix would do; whether it reaches memory is SDO's job.
- **Turn ledger.** Every scripted turn records `sdo-scripted-turn-<hash>` (kind, session, requests, usage, commands, outcome), which the harness reconciles with receipts, the exported usage logs and the run records.

## Findings and fixes

- **F1: the verify burst misses a fresh deny-all NetworkPolicy.** `sdo incident status` reported healthy about 4 s after the policy was created, on all three scenarios, because Calico does not cut established connections. Only the static `health-objective` detector flagged it. Not fixed here (it is a prober or detector-coverage question, not plumbing); reported.
- **F2 (harness): the missing-configmap plan could not restore `mongo-geo-script`.** No manifest under `kubernetes/` defines it; SREGym builds it from the root `k8s-geo-mongo.sh`. The plan stopped with a failed result, and the incident sat open for the whole 420 s stage timeout. Fixed in `2e043ea`: the plan and the learned `repair.sh` fall back to `k8s-<svc>-mongo.sh`, `repair.sh` applies only a manifest whose kind is ConfigMap (the old grep would have re-applied the Deployment), and a stopped plan records `plan_error` in the turn ledger.
- **F3 (adapter): a stuck stage failed with a message that said nothing.** "verified no new incident within 420s" did not say that an incident was open, that the responder reported `failed`, or why. Fixed in `bc94e8c`: the error names the open incident, the responder status and notes, any dispatch error and the detector-review reason. Decision: keep waiting the full timeout instead of failing fast on `detector_review_required`, because the controller still closes the incident if health clears later.
- **F4 (controller + broker, real bug): late recovery was credited to the responder.** When health stayed firing past the controller's verification window (120 s), the controller set `detector_review_required`, but a later clear (an operator fix, or here the harness recovering the fault) still closed the incident and dropped every trace of the review. The broker then saw all-clear health, and a responder that claimed a wrong fix (`wrong_only_claimed`) became a SUCCESS: reflection would learn its false cause. Fixed in `3dd7d95`: the closure carries `detector_review_required_at` and the reason; the broker treats that health as unverified for the responder (`partial`, no `verified_at`, no reflection); strict receipt validation rejects a receipt with the marker. Alternatives rejected: refusing to close (leaves the controller wedged for good), or classifying it as `failed` (the responder may have been right but slow; `partial` says exactly what is known).
- **F5 (harness): the NP wrong fix crash-looped `recommendation`.** Restarting the isolated service under deny-all put it into CrashLoopBackOff; after the policy was removed it needed more than the fault driver's 300 s health window to come back, so the fast loop stopped. Fixed in `3f289a2`: the wrong fix restarts `frontend`, the caller, which is just as wrong and does not break recovery.
- **F6 (controller, real bug): detector review crash-looped a persistent controller until its Job died.** Every controller start re-checked the persisted review flag and exited with an error. The `sdo-controller-run` Job restarted it seven times in about 15 minutes and then failed (`BackoffLimitExceeded`): no detection for any later incident, and the open incident could never close, so no outcome was recorded. Observed live on `assure-c0` after the `wrong_only_honest` incident. Fixed in `bd1e9ff`: one-shot (`--exit-after-closure`) and bounded (`--duration`) runs still end on review, matching how `ClosureFailureError` already behaves; a persistent controller reports the review once on stderr and keeps evaluating. Together with F4, the late close is recorded as `partial`.
- **F7 (my own regression, caught by the suite): a zero review time on every closure.** Go's `omitempty` does not omit a zero `time.Time`, so after `3dd7d95` every closure carried `detector_review_required_at: 0001-01-01T00:00:00Z` and the broker classified every in-time recovery as `partial` (no reflection, strict receipt rejected). The first `sequence` incident failed on exactly that. Fixed in `7bbaaeb` (pointer field, test that an in-time closure has no review marker).
- **Harness: an abandoned incident must settle and reach memory exactly once** (`90c1820`). The first `wrong-then-correct` failure lost its outcome: the stage replaced the crashed controller, and the harness never checked. `controller-settled` and `outcome-recorded` now fail such a run.
- **Harness: a killed run leaves its fault behind.** Stopping a run mid-incident left `deny-all-recommendation` in place; the next `--fresh` run then refused, loudly, because the active topology no longer matched the lifecycle attestation. I removed it by hand. Stopping a run is operator action, so this was not automated.
- **F8 (residual risk, not fixed): diagnosis verification cannot tell who fixed it.** After `wrong_only_claimed`, `verify_diagnosis` marked the false cause ("frontend pods are wedged") as `confirmed`, because the explained detectors flipped once the harness recovered the fault and a live observation cannot be checked. With F4 the late recovery is `partial` and nothing is learned. If an operator fixes the fault inside the 120 s verification window while the responder claims a wrong fix, SDO would still record SUCCESS and learn the false cause. Closing that gap needs attribution: for example, requiring the repair actions to touch a resource the verdict names, or a state-change citation. It is a design question and is reported, not patched.
- **F9 (controller, real bug): a killed responder pod wedged the controller in a hot loop.** The responder Job has `backoffLimit: 0`, so deleting its pod failed the Job. The controller treated that like a transport error and re-ran the dispatch effect, which rejoined the same failed Job by name: about 7,950 failed dispatches in 10 minutes. The incident could never close, and every later incident was locked out. Fixed in `a0fe62e`: `ResponderJobFailedError` is terminal. The responder is done with no result, `dispatch_error` is recorded, health alone decides closure, and the broker records `failed`. Transport errors still rejoin. Alternative rejected: dispatching a second responder Job. That would break the exactly-once dispatch invariant the strict receipt checks, and a replayed repair is not safe in general. The `chaos-kill-responder` expectation is now a loud, unlearned failure.
- **Residual, not fixed: transient dispatch errors retry with no backoff.** The same re-execute path serves transport errors (for example during an API-server pause). With F9 fixed it ends when the API returns, but it spins while it is down.
- **F10 (controller, real bug): a replaced prober pod was unreachable for the running responder.** Responders got the prober's pod IP at dispatch. After `kill-prober`, the controller recreated the pod at once, but with a new IP. Every `sdo incident status` in the responder then timed out after 90 s (`prober unreachable`), and the responder was still polling after 8 minutes. Fixed in `e7678f4`: the controller keeps a ClusterIP Service `sdo-prober` and gives responders `http://sdo-prober.<ns>.svc:8080`; the controller's own client keeps the pod IP, which it refreshes. The controller Role gains Service create/delete. Alternative rejected: re-resolving the pod from the `sdo incident status` CLI (it would put Kubernetes lookups in the responder's verification path).
- **F11 (controller, real bug): closure retries stalled under maintenance pause.** The persistent stage pauses the controller once health is verified. A paused controller slept an hour per loop and ignored timer ticks, so after `chaos-broker-reject` (the validator rejected a reflection with `persistence.firing: 5`) the scheduled retry never ran. After 13 minutes it still had one attempt, and the drain waiting for its acknowledgment deadlocked. Fixed in `152852c`: while paused, the controller wakes for the next closure retry and runs only closure and acknowledgment effects.
- **F11 also deadlocked teardown.** A `--fresh` run after the wedged broker-reject incident sat in teardown for more than 30 minutes, draining a closure whose retry could never run. I deleted `hotel-reservation-sdo` on `assure-c1` and set its persistent-state file aside (`sdo_persistent_controller.stale.json`). The fixed controller does not need this.
- **F12 (broker, real bug): a reflection backend that always fails wedged the persistent controller.** A turn that raised (the model CLI exited 1) did not count toward `max_reflection_attempts`. Each broker run retried it until the controller's 8 closure retries were spent, and the closure then failed permanently. A persistent controller with a permanently failed closure opens no new incident, so the next fault (`chaos-concurrent-commit`) was never even detected. Fixed in `9adafb7`: a failed turn counts, its error is kept as `reflection_backend_error`, and once the attempts are spent the broker records `no_change` with that reason and completes the closure without learning. `a2af616` puts a permanently failed closure into the stage's timeout error. The `chaos-reflection-crash-always` expectation changed from a loud failure to "completes, learns nothing, at least 2 attempts".
- **Residual, not fixed:** any other permanent closure failure still blocks later incidents in a persistent controller until an operator intervenes. It is now loud (the stage error names it), but it is not self-healing. Letting a controller skip a closure it could not commit would drop an outcome, so this is left as a deliberate, loud stop.
- **Residual, not fixed:** a broker killed during a reflection turn (for example SIGKILL) does not count that attempt. Only turns that raise are bounded.
- **F13 (controller, real bug): whether a repeat took the warm path depended on detector timing.** A learned incident detector fires on its first match (`firing: 1`), about 2 s after injection, before the health detectors. In `first-repeat` the repeat's request held only that finding (`deny-all-networkpolicy-isolation/...`), which shares no fingerprint with the prior outcome (whose findings were `health-objective/...`). The controller surfaced no relevant outcome and the responder ran a cold diagnosis. In the `sequence` run the batch happened to also hold the health finding, and the repeat went warm. Fixed in `7981c17`: outcome retrieval also matches a prior success when a detector learned from it (`originatingIncident`) fires on the same resource (`learned-detector-origin`), and the warm path treats that as exact. A learned detector on another resource (the `mongo-rate-script` variant) stays a variant. Alternative rejected: delaying dispatch until the health detectors fire. That would slow every learned incident to fix a matching problem.

- **F14 (controller, residual from F9): transient dispatch errors retried with no backoff.** The retry path F9 (`345fba0`) left in place for transport, watcher, and leadership-guard errors re-executed the dispatch effect the instant a failed completion came back, with no delay: a paused API server would have been hammered at the runtime loop's own cycle rate for as long as it stayed down. Fixed in `4ade4e2`: `DispatchRetryPolicy` adds bounded exponential backoff (2s default, capped at 2 min) with equal jitter, so several controllers recovering from the same outage do not retry in lockstep. Backoff state (attempt count and next-retry time) resets on a fresh incident, a successful dispatch, or a terminal (F9) Job failure; none of those should inherit a stale retry timer. `NextWake` now also wakes for a pending dispatch retry, and the jitter draw is injectable (`Controller.dispatchJitter`) alongside the existing injectable clock (`Controller.now`), so the backoff schedule is exact and deterministic under test. This state is not persisted across a controller restart: a restart simply retries immediately rather than waiting out the remaining backoff, which is safe (retries stay idempotent and rejoin the same Job) if less smooth. Terminal (F9) dispatch failures are unaffected and never retry through this policy.
- **F15 (broker, real bug): a broker killed mid-reflection did not count that attempt.** F12 (`ee4cb8a`) bounded a reflection backend that raises by counting the attempt in the `except` handler after `resume()` returned. A broker process killed while `resume()` was in flight (a SIGKILL, not a Python exception) never reaches that handler, or any other code in the process, so the attempt went uncounted; the next restart saw `reflection_started=True` with `reflection_attempts` unchanged, and could retry the same incident's reflection indefinitely under repeated kills, defeating the F12 bound. Fixed in `3257ccc`: `reflection_attempts` is now incremented, and saved, immediately before the backend call rather than after it returns or raises. The existing "started but not backend_completed" recovery path (rollback partial edits, clear `reflection_started`) needed no change, because by the time it runs the attempt it is cleaning up after is already durably counted, whether `resume()` failed, was rejected downstream, or the process never came back at all.

## Chaos not run

- **Disk-full: not run.** kind's `local-path` provisioner backs the repository PVC with a host directory. It enforces no capacity, so filling the PVC fills `/mnt/data`, which is shared with live evaluations and must keep at least 100 GB free. A safe version needs a size-limited volume, for example a loop-mounted filesystem under the node's local-path root, or a `tmpfs` `sizeLimit` volume substituted for the repository PVC. That changes the install topology, so it is left as a follow-up rather than approximated.
