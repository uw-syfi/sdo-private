## What the runner supports (and why the stream is generated)

- `sequence_len`/`sequence_seed` (`experiment.py`, `third_party/sregym/sregym/parallel_runner.py:148`) sample problem ids uniformly **with replacement** (`random.Random(seed).choice`) from the selected problem list. They give repeats by chance only, no parameter variants and no controlled mix, and they belong to plain `[runner]` experiments, not to pipeline stages: a persistent-controller pipeline is a list of `[[stages]]`, each with its own `problems`. There are no composed faults in this path (`MultipleIndependentFailures` is commented out in the registry).
- The `variants` mode (`--variants`) generates `__v_` ids from `variant_specs.py` but is likewise mutually exclusive with explicit `problems` and not stage-aware.
- **Decision: generate the stage list from the seed** (`benchmarks/sregym/runner/incident_stream.py`, seed `20260930`, 24 incidents) and render the pipeline TOML for SDO and the `problems` list for the baseline. Alternative: `sequence_len = 24`. Rejected: uniform sampling over about 40 hotel problems would almost never repeat a class within 24 incidents.
- Stream rules: 4 core classes (first occurrences), 3 novel one-off classes, 8 parameter variants (never seen before), 9 exact repeats. Every repeat/variant follows its family's first occurrence; the first 8 incidents (the pilot) hold all four firsts plus at least one novel, one exact repeat and one variant; every core fault recurs exactly at least once; no fault twice in a row. Rejection sampling from `random.Random(seed)`, so it is deterministic. `test_incident_stream.py` checks these and that the committed TOMLs equal the generator's output.

## Measurement and harness decisions

- **Judge time**: the grading mode is the default (diagnosis judged before the mitigation stage opens), with the headline judge-free TTM computed by `incident_cost` (grading wait subtracted, floored at the last state-changing command). `defer_diagnosis_grading` is **not** used: it changes when the mitigation stage opens, and TTM is comparable only within one grading mode; the default mode is the one all earlier luna logs use. The lifecycle validation cache is unused (stage 0 runs the cold lifecycle, so the stream includes the one-time lifecycle, reported apart from incidents). `fast_namespace_teardown = true` on both arms: it only skips pod termination grace between incidents, outside every measured window.
- **Codex CLI version**: SDO images run Codex 0.157.1 but the stock Codex agent installs npm `latest` at container start (now 0.159.2; 0.158.0's platform package 404'd, which is the pin commit `cbb9715f` on another submodule branch). Pushing a submodule branch was not possible in this session, so instead of bumping the pointer the baseline is launched through `benchmarks/sregym/registry.yaml` with `agent_version: "0.157.1"` (test: matches `controller/Dockerfile.runtime`). No harness change.
- **Codex quota**: the shared ChatGPT window was at 91 % used at the start (resets 2026-10-03 18:19 UTC). Same stop rule as earlier runs: no new stage is started at 97 % or more.
- **pytest basetemp** is set to a private directory (`PYTEST_ADDOPTS=--basetemp=…`) because the shared `/tmp/pytest-of-shli` garbage collection warns about removing other users' directories.

## Pilot attempt 1: a fault SDO cannot observe or repair (stream revised)

- **Launch**: commit `250a4a8`, SDO on `stream-w10` and baseline on `stream-w11` (both created by the harness: 1 control plane + 1 worker, 3 CPUs per worker, Calico with enforced NetworkPolicy, images `sdo-*:stream1`), `20260930_065110_pipeline_sdo-codex-luna-stream-pilot` and `20260930_065110_codex` under `third_party/sregym/logs/` (in the `stream-lc` worktree). `stream-w12` (3 workers) was only the no-LLM fault-verification cluster and was deleted before the pilot; the topology of the run clusters was checked with `docker ps` and `docker inspect` (NanoCpus 3e9).
- **Finding**: incident 5 was the "novel" `service_dns_resolution_failure__v_hotel_reservation_frontend`. Its injector edits the `kube-system/coredns` ConfigMap (an NXDOMAIN template). SDO's controller observes and repairs only the application namespace, so no detector fired (`findings: []` for 30 minutes of controller iterations) and no responder ran. The stock Codex baseline also failed that fault (both times, oracle false). My earlier verification checked injectability and oracle behaviour but not whether a namespace-scoped agent can see or fix the fault; that was a mistake in the fault-vetting step, not an SDO bug.
- **Decision: drop the fault from the stream; keep the completed prefix.** Novel count 3 becomes 2 (`misconfig_app_hotel_res`, `wrong_dns_policy_hotel_reservation`) and exact repeats go from 9 to 10. Alternatives: (a) wait out the 3600 s agent timeout and continue (the same fault came again at incident 7 and would have left an NXDOMAIN template that breaks the next incident's DNS; rejected); (b) verify one more novel candidate on another private cluster (about 15 more minutes; rejected, two novel classes are enough for a pilot; recorded as a limitation).
- **Decision: pin the opening (`STREAM_OPENING`).** Incidents 1-4 (network_policy_block, missing_configmap, readiness_probe, network_policy_block repeat) of the first attempt completed with valid strict receipts and were unaffected by the revision, so the seed now samples only incidents 5-24 and the first four stay as run. Alternative: rerun everything on a freshly sampled stream (re-pays the cold lifecycle, about 1M tokens, ~15 min, when the Codex weekly window is at 91 %+). The pinning is disclosed here because it makes the first four incidents chosen by hand-of-history rather than by seed. Baseline runs 1-4 (memoryless) are likewise reused.
- **Kill**: I terminated my own SDO pipeline processes (not any other process) during incident 5, removed the leaked NXDOMAIN template from `stream-w10`'s CoreDNS (patch + rollout restart on my cluster only), and will resume the pipeline from stage 4 with `run_sregym.sh <pipeline-dir> --stage 4` against an edited pipeline snapshot. This is not a clean resume test (criterion 4): it is a defect-driven abort. The extension from incident 8 to 9 will exercise resume with a clean shutdown.
- The baseline pilot on the old stream ran 8 incidents (3/8 solved). Its runs 5-8 belong to the discarded stream and are kept only as supplementary evidence (`20260930_065110_codex`).
