## What the runner supports (and why the stream is generated)

- `sequence_len`/`sequence_seed` (`experiment.py`, `third_party/sregym/sregym/parallel_runner.py:148`) sample problem ids uniformly **with replacement** (`random.Random(seed).choice`) from the selected problem list. They give repeats by chance only, no parameter variants and no controlled mix, and they belong to plain `[runner]` experiments, not to pipeline stages: a persistent-controller pipeline is a list of `[[stages]]`, each with its own `problems`. There are no composed faults in this path (`MultipleIndependentFailures` is commented out in the registry).
- The `variants` mode (`--variants`) generates `__v_` ids from `variant_specs.py` but is likewise mutually exclusive with explicit `problems` and not stage-aware.
- **Decision: generate the stage list from the seed** (`benchmarks/sregym/runner/incident_stream.py`, seed `20260930`, 24 incidents) and render the pipeline TOML for SDO and the `problems` list for the baseline. Alternative: `sequence_len = 24`. Rejected: uniform sampling over about 40 hotel problems would almost never repeat a class within 24 incidents.
- Stream rules: 4 core classes (first occurrences), 3 novel one-off classes, 8 parameter variants (never seen before), 9 exact repeats. Every repeat/variant follows its family's first occurrence; the first 8 incidents (the pilot) hold all four firsts plus at least one novel, one exact repeat and one variant; every core fault recurs exactly at least once; no fault twice in a row. Rejection sampling from `random.Random(seed)`, so it is deterministic. `test_incident_stream.py` checks these and that the committed TOMLs equal the generator's output.

## Bug found: a paused controller never retries a rejected closure (stage 18 stalled 27 min)

- **Symptom** (orchestrator check-in 10:20): incident 19 (exact network_policy_block) sat silent from 09:59:52. The application, detectors and harness were fine; the *previous* incident's (18, exact readiness probe) closure was pending: `closure_state: pending`, `closure_failure.attempts = 1`, `next_attempt_at = 09:58:20`, and no controller output after the rejection at 09:58:18. The next stage's reflection drain (`_wait_for_reflection_drain`) waits for that acknowledgement, so it was a deadlock, not a slow agent.
- **Root cause** (`controller/runtime/run.go`): the persistent benchmark mode pauses the controller once health is verified. While paused, the run loop's delay is a fixed `time.Hour` and the timer case just `continue`s, so the bounded closure retry (3.4-a, "8 attempts with backoff") never fires. The design says in-flight closure, reflection and acknowledgement continue while paused; only the retry wake did not. Any rejected closure in persistent mode therefore blocks the pipeline until the drain timeout (3600 s) instead of retrying.
- **Why the first closure was rejected** (`sdo/operational_memory/broker_service.py:590`): reflection changed only playbook files, and `_learned_incident_detector_fired` looks at `closure.request.findings`, i.e. the findings batched at dispatch. The learned detector `frontend-readiness-probe-mismatch` fired 13 s after the health detector had already dispatched the incident, so its finding was not in the request; the broker demanded a detector update, rejected the proposal and raised. The retry (fresh session with feedback) would normally succeed. This is a second, smaller finding: a warm exact repeat can be treated as an ordinary incident when the learned detector's persistence delays its finding past dispatch. Not fixed here.
- **Fix, test-first** (`TestPausedControllerStillWakesForAPendingClosureRetry`): `Controller.PausedWake()` (the closure retry time only, zero when none is due); the paused branch sleeps until then and its timer case runs pending effects (never a detector step). `go test ./controller/runtime/...` passes. **The fix is not in the images used by this run** (`stream1` was built before it); rebuilding mid-run would change the software under test. Every later stage still carries this bug, so any other rejected closure in the remaining stages can deadlock the same way.
- **Unblocking the running stage (operator action on my own cluster `stream-w10`)**: patching the maintenance ConfigMap to `active` did not help (the resume needs the application-namespace Role the driver grants only at the next stage, so observation timed out; I restored `paused`). I then terminated the Go controller process inside the controller pod (pid 1629, via `kubectl exec`); this took down the supervisor's pod and the Job started a new pod (`sdo-controller-run-drbc2`, new UID), which on startup executed the pending closure effect, committed it and logged `controller_closure_restart` at 10:33:20. Stage 18 then continued. Cost: the persistent controller has a new pod UID for incident 19 onward (the "same pod UID" reuse check will show two UIDs), and incident 19's wait is long because of the stall; its judge-free TTM is unaffected because the fault is injected only after the gate. The stall is reported as a harness/controller defect, not as an SDO latency.
