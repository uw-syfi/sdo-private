Self-Defining Operator

The paper's SDO is an autonomous Kubernetes operator whose behavior is partly written by prior responder agents: durable memory, detectors, playbooks, and reflection turn resolved incidents into faster future responses.

Operational Memory

Versioned in the application repository and edited by reflecting agents.

arch.md

Compact model of services, dependencies, config, and build/deploy structure.

goal.md

Human health objective: endpoints, correctness checks, and operating requirements.

playbooks/

Parameterized diagnosis, repair, and verification procedures distilled from incidents.

detectors/

Deterministic code over cluster state that flags known faults and surfaces playbooks.

Outcome log

Append-only success, false-positive, and false-negative signals for detector refinement.

SDO Runtime

Fixed interfaces constrain what agents can write; agents fill in the operational content.

Monitor

Runs registered detectors continuously without LLM calls.

Responder subagent

Confirms surfaced playbooks or investigates from scratch, then mitigates.

Reflect step

Writes or revises playbooks, detector code, architecture notes, and outcome routing.

Validation gates

Detector compilation, playbook references, health checks, and commit rules guard memory.

Operated System

The application source and live cluster are the source of truth for action and observation.

Application repository

Contains source, manifests, deployment code, and SDO memory.

Kubernetes cluster

Monitor observes typed cluster state; responders inspect and apply repairs.

Deploy pipeline

Commits are deployed so fixes and detector updates become live behavior.

SREGym evaluation

Current experiments inject benchmark faults and grade diagnosis plus mitigation.

1. Detect

Monitor evaluates detectors over cluster snapshots.

2. Dispatch

Persistent findings wake a responder with bound resources.

3. Resolve

Responder confirms playbooks or investigates hypotheses.

4. Reflect

Successful work becomes playbooks, detectors, and routing updates.

Paper Pieces Not Fully Matched

Detector controllerThe paper describes compiled detector code in a Kubernetes controller; this repo mainly uses KB retrieval and subagent verification.
.sdo/ layoutCurrent memory is under SREGym experiment KB dirs, not exactly the paper's repository-local .sdo tree.
Outcome logThe current code records benchmark/stage outputs and histories, but not the exact detector FP/FN outcome-log mechanism.
Always-on monitorSREGym starts incident runs on demand; the paper's monitor operates continuously and dispatches responders when detectors persistently fire.
Source-of-truth commitsThe paper emphasizes every repair and memory change as app-repo commits; SREGym runs often patch live benchmark clusters.
